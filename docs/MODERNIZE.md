# maplace.js modernization

Single source of truth for the 1.0 rewrite. Read this first; it is written to be enough on its own. Lives in `docs/` with the RFC and future decisions/specs.

Now: headless core done (C1–C6, C8) with its 0.2 regressions as tests (C7); the list view is done (V1); the adapter conformance suite runs on the fake (T9), in Chromium with the V1 browser checks (T2); the Google adapter draws markers and shapes, editable ones reporting their edits, and their popups, and follows the store's views, reporting what it shows, keeps them through hidden or resized containers, and holds the page's views as on-map controls (G1–G5, G8–G10), draws the store's route (G6), clusters markers (G7), and runs every conformance group on real Maps JS in CI, on a map it creates and on the page's own; it reports a refused key and a page map without a map ID as load errors (G9). `<maplace-map>` works on any provider, with load states and hold for consent (V3, V7), and draws on Google from its own attributes, loading Maps JS itself (V3b). Sizes are budgeted to what 1.0 measures and checked by `npm run check` (P10, P3). The package builds: npm ESM and `.d.ts`, the two CDN scripts, the package staged as npm packs it (P1, C6), checked as a consumer gets it: publint, attw and a strict consumer type-check (T4). Coverage floors are a CI gate (T8); CHANGELOG.md and its check exist (P4). The release workflow and its notes are built and tested, first run after R3 (P2, P5). The README and MIGRATION.md are written, their snippets held to the examples (P6, P7), and every example runs, on the fake each push and the pages on real Maps on `next` (T5). The site has its shell, look and consent gate, and every example live on the home page with 0.2's data, tested end to end (W1, W8, D24, W2, W4). Events say what changed (`selectionChange`, `routeChange`, …), MIGRATION's event table held to them (V9, D25). The list and popups have default styles, and the select lists fit all once (V10); selecting a shape fits it and draws it heavier (V11), and shapes take their own selected and hovered styles (V14). Routes report their steps and pass through via stops (G11, G13). Users' live edits and clicks on the map are events (C11, C12). Every code tab is the live map (W13). A location has its own zoom and can stay out of the list (C9, C10); the element takes map settings (G12) and list views registered by name, with a heading (V15, V16); a route result names its route (G14). Next: examples as rich as 0.2's demos (W14); then the site redesigned on Tailwind (W12, D26) and the reference pages (W1b).

## Conventions
- Tooling stays simple: plain npm, few deps, no framework where a script will do.
- CHANGELOG.md: one dated line (`- YYYY-MM-DD Added/Changed/Fixed/Removed …`, the verb required: it sets the release's smallest bump, P2) per change a reader would notice, at the top, in the same commit; a closed issue as `#N` at the line end. A test reads git history and fails if a commit that closes an issue has no line (keywords and baseline in P4). Lines above the first `## <version> (<date>)` heading are unreleased: a release puts its heading above them, and its notes are those lines; a stable release also ships its pre-releases' sections below its heading, judged and noted with them (P2, P5). The site renders it at `/changelog`.
- Releases: manual GitHub Actions dispatch with a version; refused unless above every released version (P2); pre-releases only to dist-tag `next`; workflow tags `v<version>` and publishes via npm trusted publishing (GitHub OIDC, no `NPM_TOKEN`; needs npm ≥ 11.5.1, i.e. current Node LTS; provenance is automatic). Checkout uses `fetch-depth: 0` (the CHANGELOG test reads history). The first release (1.0.0) is manual (R2); P2 takes over after R3, since dispatch and schedules only run from the default branch. Releases come from `main`'s head (`next` retires at R3): the release commit (version and CHANGELOG heading) is made, then verified, then tagged and pushed with its tag atomically; publish and the GitHub release are jobs of their own, each re-run alone and skipped when already done.
- Deploys: every push builds; branches → Cloudflare preview alias named after the branch (noindex); production from `main` only after R4.
- Offsite check: a script fetches live pages like a browser and fails if anything loads from an origin not on the allowlist; runs after each production deploy and daily once R3/R4 are done (Cloudflare can inject scripts the build never sees).
- Docs examples are executed by tests, so docs can't drift. A fix lands with a test shown failing first.

Sources for D5–D8: developers.google.com/maps/documentation/javascript/ `advanced-markers/migration`, `cloud-customization/troubleshoot` (map ID + JSON styles), `routes/route-class-overview`, `releases` (Routes JS dates); github.com/googlemaps/js-api-loader issue #1083 (importLibrary right after setOptions).

## Rejected (don't re-propose without new information)
| Option | Why not |
|--------|---------|
| pnpm, Turborepo | user prefers plain npm; no benefit at one package + one site |
| `@maplace/*` scoped split | core is useless without an adapter (two installs for anything); per-package versions are overhead for one maintainer; npm org needed |
| tsup/tsdown, Vite lib mode, Rollup | esbuild + tsc is two well-known tools and a short script |
| ESLint + Prettier | two tools and more config; Biome does both |
| `node --test` | would need hand-rolled DOM mocks, coverage and browser mode; Vitest has them |
| Changesets, semantic-release | manual dispatch + hand-written changelog preferred |
| Hand-rolled site build, Vite MPA, Starlight/VitePress | Astro gives MDX docs + islands (the React examples) with one dependency |
| Own Worker analytics, Plausible, GA | user chose Cloudflare Web Analytics: zero code, cookieless (listed on the privacy page; allowed before consent since it sets no cookie) |
| Per-map consent, banner-only | per-map is too much friction on an examples site; banner-only doesn't gate Google's cookies |
| Site looks "Atlas" (paper, serif, contour lines), "Survey" (graphite, mono, coordinate grid), and the full transit poster (the page as one line, each scenario a station in its own colour) | D24 keeps the transit type and accent, without the spine and the ten colours |
| Legacy `google.maps.Marker`, JSON `styles`, no-mapId fallback | Marker deprecated (2024); JSON styles ignored with a mapId; a fallback means two code paths |
| `DirectionsService` | legacy, replaced by Routes JS `Route`; risk accepted that Routes JS is young (weekly 2025-10-23, now also in quarterly) |
| Bundling DOMPurify, Trusted Types | size, and the user picks their own sanitizer; text-by-default makes most data safe without one |
| Merging `develop`, its `this.scope` refactor | moot after the rewrite |
| Public beta, README "rewrite in progress" notice, early npm placeholder | nothing public until stable (user); beta testing is private (R0) |
| Several routes per map, route alternatives | D22 keeps one route per map (A0: #78, #177) |
| Built-in traffic/bicycling/KML layers, distance matrix, drawing, print | add them to the user's own map (G1) or use Google APIs directly; beyond a location/route manager (A0). Places is not rejected: N12 |
| Providers other than Google/MapLibre, Vue/Svelte wrappers, 0.2 compat shim | scope; the element covers other frameworks; MIGRATION.md covers 0.2 |
