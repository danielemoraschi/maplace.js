# CLAUDE.md

maplace.js is being rewritten from scratch as 1.0. Three documents, one job each:
- `docs/MODERNIZE.md`: context, decisions history, rejected options and the status of every task. Read it first; update a row's status with the work, and add rows rather than new planning files.
- `docs/rfc-1.0.md`: the 1.0 API (frozen).
- This file: how to work in the repo.

## Commands
Node 24 (`.nvmrc`). Scripts in `scripts/` are TypeScript run directly by Node.
- `npm ci`: install; then, once, `npx playwright install chromium` for the browser tests.
- `npm run check`: Biome (lint, format, file length, `google.maps` only in `src/google/`), then `scripts/check.ts`: import layers, RFC ↔ types, MIGRATION's Events table ↔ `api-lists.ts` (its 1.0 event column), the size budgets of RFC §3 Numbers (the builds made in memory with `npm run build`'s options, minified and gzipped; the budgets are read from the RFC table), CHANGELOG, doc links (every relative link in the docs reaches a file), doc snippets (a fence after `<!-- example: <path> -->` is a copy of that file) and workflows (every `.github/workflows/*.yml` parses as YAML: GitHub runs no job of one that doesn't).
- `npm run sizes`: each budget with what it measures now and the headroom left.
- `npm run coverage`: after `npm test`, the line coverage of the core (what the `maplace` entry loads) and of the package against the floors of RFC §3 Numbers; a CI step.
- `npm run build`: `packages/maplace/dist` (npm ESM and `.d.ts`, the two CDN scripts), then `packages/maplace/packed`, the package as npm packs it (no `maplace:source`).
- `npm run release <version>`: what the release workflow (`.github/workflows/release.yml`, P2) runs first, in this checkout: the version written (manifest, lockfile, `MAPLACE_VERSION`) and the unreleased CHANGELOG lines headed `## <version> (<date>)`, or why the version can't be released; `npm run release-notes <version>` prints that version's GitHub release notes. A local run is a rehearsal: undo it with `git checkout`.
- `npm run typecheck`: source, examples, type tests, then `scripts/`, then the site's `.ts` (`apps/site`).
- `npm test`: Vitest, with a coverage report (`coverage/lcov.info`): the `node` project (node and happy-dom) and the `browser` project (`*.browser.test.ts`, headless Chromium, served from `localhost:63315` when the port is free); `--project <name>` runs one. Tests on real Google Maps run when `VITE_MAPS_KEY` is set (in `.env.local`; the key must allow `http://localhost:63315/*`) and skip otherwise; CI runs them on `next` when a push needs them (below). Among them, `apps/site/test/examples-on-google.test.ts` runs every section's versions on the built site's group pages, its visitors seeing it at `localhost:63315` through Playwright's routing, so it binds no port and runs beside the dev server; its MapLibre twin, `apps/site/test/examples-on-maplibre.test.ts`, does the same on every push, OpenFreeMap's styles answered from the machine. The node project also checks the package as npm would pack it (built into temp dirs): publint, attw, and a strict consumer type-check (`scripts/checks/packed-package.test.ts`).
- `npm run fix`: Biome's safe fixes and formatting.
- `npm run site:dev`, `npm run site:build`: the site (`apps/site`, Astro) in dev, or built into `apps/site/dist`. The site pins the CDN scripts it shows to their integrity, hashed from the scripts built in memory as they are published, and links the repo's files at the commit it is built from. CI checks the site through `npm test`, which builds it; `deploy-preview` builds it again for upload. `SITE_MAPS_KEY` gives its maps a key (W6's, referrer-restricted); without it `astro build` warns, and a map asked to load says the site has no key. `SITE_MAPS_MAP_ID` gives them the site's own map ID (W15): written into a page's map that sets none, and the default of the vanilla and React versions' `maplace/google` and of the site's `Maplace` the script versions call (`src/site/example-map-id.ts`, through `astro:env/client`); without it `astro build` warns and the maps run on Google's `DEMO_MAP_ID`, warning of it. There is no `astro check`: it needs TypeScript 6 or older, so the site's logic lives in `.ts` modules that `npm run typecheck` checks, and its `.astro` files only arrange them.
- `npm run sonar`: SonarQube scan (scope in `sonar-project.properties`, host and token from `.env.local`); it lands on the same main branch as CI's, so use it to check before a push.

CI (`.github/workflows/ci.yml`) runs `check`, `typecheck` and `test` on every push. A tracker row that adds a gate adds its CI step in the same commit. On `next` it also sends the analysis to SonarQube, report-only. On `next`, `npm test` gets the `MAPS_KEY` secret, so the Google tests run on real Maps JS there, each map billed: only when `next` changed more than prose (`*.md`) or MapLibre's own files since the last commit CI's `verify` passed on it (a `maplibre` in the file's or a folder's name; `scripts/checks/real-maps.ts`), or for a run started by hand (Actions → CI → Run workflow on `next`). Once `verify` passes on `next`, `deploy-preview` builds the site with `SITE_MAPS_KEY` (secret) and `SITE_MAPS_MAP_ID` (variable), failing without either, and uploads it with Wrangler as a version under the alias `next` (`apps/site/wrangler.jsonc`, Worker `maplacejs`, created once in Cloudflare's dashboard since an upload can't create one; `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`; the Worker's script answers `/api/stars` with GitHub's star count, its token the Worker's secret `GITHUB_STARS_TOKEN`, set once with `wrangler versions secret put` and carried by the versions uploaded after it): `next-maplacejs.<subdomain>.workers.dev`, every version URL behind Cloudflare Access, sent with `X-Robots-Tag: noindex`; then checks that no page of it loads anything from another origin before consent (`apps/site/src/site/offsite-check.ts`, W10c; through Access with its service token, `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET`); no other branch deploys, and production waits for R4. A failed deploy turns the run red without making later pushes run the billed tests again: their base is the last run whose `verify` passed.

## Layout
- `packages/maplace/src/`: the package. Entries: `index.ts` (core), `google/`, `element/` and `react/` (the React binding, which uses the core through its entry, as the element does); `cdn/`, what each CDN script sets as the page's `Maplace` (not an npm entry).
- `packages/maplace/src/adapter-kit/`: what every adapter draws with; the fake and Google share it, the core entry never imports it.
- `packages/maplace/src/location-state.ts`: a location's state from selection and hover, shared by the adapters and the list view; `location-index.ts` beside it finds a location by id.
- `packages/maplace/src/__typetests__/`: compile-time API tests (`@ts-expect-error` must stay errors) and `api-lists.ts`, the RFC's lists of codes, events and capabilities.
- `packages/maplace/examples/`: the RFC §2 use cases, each a page, a script (`script.html`: the vanilla program on the CDN script's `Maplace`, W33), a vanilla and a React version with the HTML they mount on (`vanilla.html`, `react.html`): Google's in the example's folder, MapLibre's in its `maplibre/` (ids `<name>-maplibre-*`; route Google only, as MapLibre has no routing, `GOOGLE_ONLY` in `src/testing/examples/example-files.ts`; quick-start a page on each); type-checked, never published. `src/testing/examples/` runs them. An example may carry a `guide.md`, which the site renders under its section; `scripts/docs/example-guides.ts` finds them, for the site and for `DOCS`, so their links are checked like any doc's.
- `scripts/`: repo checks, each in `scripts/checks/` beside its test; the build's definitions in `scripts/build/`, which the size check measures too; `scripts/docs/`, the Markdown and CHANGELOG readers the checks, the build, the release and the site share; `scripts/recipes/`, scripts the docs show readers, each copied word for word into its page and run in its test.
- `apps/site/`: the website (D23, D24). Its logic is in `src/{site,examples,consent,scripts}/*.ts`, and its Worker's in `src/worker/` (W44: the star count, run first for `/api/stars` only), tested in the node project, and its pages end to end in `test/*.test.ts` (the site built, served, and driven in Chromium with every request off the machine refused; builds take turns under `test/build-lock.ts`, since two concurrent `astro build`s clobber each other). Repo files reach it through Astro's content layer (`src/content.config.ts`), which runs unbundled: a bundled page can't find the repo. Its CSS (D26): Tailwind utilities on the markup the site writes; `src/styles/prose.css` (rendered Markdown, Shiki's output) and `frame.css` (an example's own nodes in the frame, every rule matching at any depth and in no layer, or the library's unlayered `:where()` defaults would win) for markup it doesn't; no preflight, so an example looks on the site as on a reader's page. The pages in `MARKDOWN_ROUTES` (`src/site/markdown-routes.ts`) are also at `<route>index.md`: `src/pages/[...twin].md.ts` writes them from the collections' `body` (`markdown-twins.ts`), the same Markdown the page renders; `/llms.txt` is built from `SITE_ROUTES` and `AGENT_LINKS`; `public/robots.txt` and `public/_headers`' `Link` rules are static, held to the routes by `test/agents-markdown.test.ts`. A route `.ts` that reads `astro:content` opens with `/// <reference types="astro/client" />`: `tsc` has no generated types, so its collections are `any` and its logic goes in a typed, tested module. The agent skill (W40): `src/site/agent-skill*.ts` write `/.well-known/agent-skills/maplace/SKILL.md` and the index beside it through the `agentSkill` collection (the routes only serve it, as `tsc` skips `.well-known`), its lists read from the API's and its snippets from the example files; `agent-skill.test.ts` holds every fence to a version the example runners run, and `test/agent-skill-served.test.ts` the digest to the served bytes.
- `README.md`, `MIGRATION.md`, `CHANGELOG.md` at the root: the package's own docs. The README's pinned CDN snippets (`maplace@x.y.z`, `sha384-…`) are filled in when the package is staged; never write real values there.
- `docs/`: the RFC and the tracker, deliberately single documents, and `docs/reference/`, the site's reference pages (one small file per page, rendered through `REPO_DOCS`, their tables held to the API by `apps/site/src/site/reference-pages.test.ts`); everything else stays small.

## Rules
- **Clean code**: intention-revealing names, small functions that do one thing, no comments that restate the code. The API's own conventions (arguments, `undefined`, errors) are RFC §3 Rules and Errors.
- **Modules**: one concept per file, 100–200 lines; Biome fails a file over 300 (`biome.json`). Split before a file nears the limit.
- **Browser tests**: what only a real browser shows (layout, scrolling, focus, trusted input, the accessibility tree) goes in a `*.browser.test.ts`, each starting with the mouse parked at its frame's bottom-right corner (`src/testing/parked-pointer.ts`), so a test that needs the pointer over something moves it there (the park assumes a file's tests run one after another: no `describe.concurrent` there); logic stays in node or happy-dom tests. Tests needing real Google Maps go under `src/google/` in `describeWithMaps` (`src/google/testing/`). The examples in `packages/maplace/examples/` run by being there: every version on the fake every push, MapLibre's on real MapLibre (offline) every push, Google's on real Maps on `next` when a push needs them (on the built site's group pages, `apps/site/test/examples-on-google.test.ts`; quick-start's page, not on the site, in `src/google/examples-on-google.browser.test.ts`); an example a reader copies is never edited to suit a test. Every example's page, script, vanilla and React versions are the same map, each a complete program (the HTML it mounts on, data, styles, behaviour), and each runs live on the site under its tab (W13); a new example comes with all four on each provider it runs on. Example versions may share a page (the site shows every one): each one's ids and top-level script names are its own (`route-map`, `routeMap`, `route-vanilla-map`, `route-script-map`), and `element/examples-together.browser.test.ts` fails on a clash or on versions that differ.
- **Layers**: what may import what is the `LAYERS` table in `scripts/checks/imports.ts`; a new file under `src/` gets a row there.
- **API changes** follow the RFC header. A new error code, event or capability also goes in `api-lists.ts`; typecheck and `npm run check` then point at anything out of step. Keep the RFC lines `scripts/checks/rfc.ts` reads in their format.
- Private phase: nothing public before the go-public gate (§9 in the tracker): `master`/`main`, npm, the live site and GitHub issues stay untouched. `next` being visible on GitHub is fine.

## Agent workflow
- Work on a short-lived branch, fast-forward merged into `next`. Commit only when asked; no attribution lines in commit messages.
- Before any change merges, run on the branch diff, in order: `/simplify`, then `/code-review`, then `/clean-code` (a user skill; skip it if unavailable and say so). Fix findings, then merge. Documentation-only changes skip the chain.
- After the chain, before committing: `npm run sonar`, then read the quality gate and open issues. A red gate is fixed, or explained to the user, before the change merges; CI's own scan is report-only.
- A fix lands with a test shown failing first.
- A change a reader would notice adds its dated line at the top of `CHANGELOG.md` in the same commit (`- YYYY-MM-DD Added/Changed/Fixed/Removed …`, the verb required, a closed issue as `#N` at the end).
- Commit message style: `[add]`, `[upd]`, `[fix]` prefix, short summary; a commit that closes an issue says `Fixes #N` (the CHANGELOG test, P4 in `docs/MODERNIZE.md`, reads it).
